# 00 · 架构

> 一句话：**一个内核，三个入口；模型只出主意，代码才动手。**

```
          ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  入口层   │ 老人端网页    │   │ 家属端网页    │   │ IM/APP 渠道   │
          │ index.html   │   │ family.html  │   │ webhook.mjs  │
          └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
                 │                  │                  │
                 ▼                  ▼                  ▼
          ┌───────────────────────────────────────────────────┐
  内核层   │ ① 意图层  parseIntent()      关键词适配器（可换 LLM）│
          │ ② 判定层  evaluate() + RULES  只读，输出 level+hits │
          │ ③ 确认层  pending / runPending()  唯一执行出口       │
          │ ④ 执行层  TOOL_IMPL[tool]()   白名单，参数校验        │
          │ ⑤ 审计层  audit()             五要素，JSONL 可导出   │
          └───────────────────────────────────────────────────┘
                                  │
                                  ▼
          ┌──────────────┐   ┌──────────────┐
  数据层   │ Mock 业务数据 │   │ 外部服务      │
          │ ACCOUNT/BILLS│   │ fx_server.py │
          └──────────────┘   └──────────────┘
```

## 五个层的不变量（改代码不许破坏）

| 层 | 职责 | 不变量 |
|---|---|---|
| ① 意图 | 一句话 → `{tool, params}` | 只做理解，不决定能不能办；认不出就返回 null |
| ② 判定 | 意图 → `{level, hits}` | **只读** `STATE`；每条命中必须有 `rule` 名与带数字的 `detail` |
| ③ 确认 | 黄级挂起、红级拦截 | **确认前工具绝不被调用**；所有"确认后执行"只走 `runPending()` |
| ④ 执行 | 真正改数据 | 只接受白名单内的工具；金额是整数分；非法参数在代码层拒绝 |
| ⑤ 审计 | 留痕 | 五要素（时间/原话/工具/脱敏参数/决策+actor），卡号只留后四位 |

## 能力矩阵（与 `docs/capabilities.json` 一一对应，由 smoke 校验）

21 个工具按场景分布，完整字段见 `docs/capabilities.json`；这里只列"分级结论"：

| 场景 | 🟢 自动执行 | 🟡 需确认 | 🔴 只拦不做 |
|---|---|---|---|
| 智能转账 | — | `transfer`（本人或家属回执）、`schedule_transfer`、`split_bill` | 单笔 >1,000、日累计 >5,000、新收款人 >200 时由规则升红 |
| 账单分析 | `query_balance`、`list_bills`、`audit_leak`（两步） | — | — |
| 订阅代扣 | `list_subscriptions`、`upcoming_renewals`、`detect_recurring` | `cancel_subscription` | — |
| 卡片管理 | `freeze_card`（止损、可逆） | `unfreeze_card`、`request_limit_change`（只提交申请）、`apply_card` | `change_password`、`report_loss` |
| 跨场景联动 | `fx_rate`（外部，2s 超时） | `birthday_plan`（锁定预算 + 到点提醒） | — |
| 理财操作 | `list_wealth`、`risk_assess` | `buy_wealth`（>5,000 由规则升红） | — |
| 无障碍 | `repeat_last`、`safety_check` | — | — |

> 分级的真正依据是**可逆性**，不是金额大小：临时冻结可逆 → 自动执行；正式挂失要换卡号 → 判红。
> 红级没有实现体也是设计：判红的东西不应该有可被调用的实现。
> 新收款人不再一律拒绝：≤200 元确认即可，>200 元才升红——**放开的是便利，不是额度**。

## LLM 放哪儿

意图层是可替换的适配器：

- 现在：`parseIntent()` 关键词 + 正则，**离线可跑、可解释、可回归**；
- 上线：换成 LLM 输出 `{tool, params}`，外面加 JSON Schema 校验。

边界是硬的：**LLM 的输出最多决定"想办什么"，决定不了"能不能办"**。判定、确认、执行、审计全在代码里，模型被注入话术骗了也调不动钱——这是 `guard.备注注入未动钱` 那条断言守的东西。

## 三个入口怎么共用一套逻辑

| 入口 | 复用方式 | 特点 |
|---|---|---|
| 老人端网页 | 页面内联脚本即内核 | 断网双击可跑，演示主链路 |
| 家属端网页 | 只共享回执算法（`shortHash`），两端必须逐字一致（smoke 校验） | 不显示操作详情，防转述误导 |
| 渠道 `webhook.mjs` | 用 `page_sandbox.mjs` 把页面脚本跑在 Node 里 | 渠道层不做判定，规则只有一份 |
| 服务 `agent_server.mjs` | 同上，加载内核后按 `session` 隔离 STATE/pending/AUDIT_LOG，暴露 `/chat` `/confirm` `/audit` | 服务形态：与单文件版判定结果逐字相同，不重写逻辑 |
| 命令行 `hello_agent.py` | 独立的教学用最小闭环（LLM Function Calling 演示） | 不是主链路，用于讲"真调工具" |

## 为什么不拆成多个模块

演示硬要求是**断网、双击、零依赖**。拆成 ES Module 会引入构建或浏览器安全限制（`file://` 下模块加载受限），反而增加演示失败面。所以采取"单文件承载内核 + 外部脚本做校验"的策略：

- 内核只有一个文件，读得完；
- 约束不靠目录结构，靠**可执行的闸门**（`check.py` / `smoke.py` / `capabilities.json` 对账）。

## 守住这套架构的四个闸门

| 闸门 | 拦什么 |
|---|---|
| `check.py` | 密钥、明文卡号、占位实现（TODO） |
| `smoke.py` 结构段 | 三色分级、确认兜底、审计导出、两端回执算法一致 |
| `smoke.py` 框架段 | `capabilities.json` 与代码的工具表/权限表/规则表不一致 |
| `smoke.py` 行为段 | 45 条行为断言：确认前不动钱、超限判红、注入未动钱、双通道、汇率降级…… |
